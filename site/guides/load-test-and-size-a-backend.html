Load-Test and Size an Observability Backend

Produce a known, adjustable load and find where your backend starts to struggle.

Before a telemetry backend takes real traffic you want answers to three questions: how much data will it ingest, what will it cost, and where does it start to struggle? OTel Studio can produce a known, adjustable load so you can find out on purpose instead of during a launch.

1. Start from a profile, not from zero

On the Scenarios page, the four Quick Start Templates set a scenario mix and an infrastructure profile in one click: Startup (one core scenario, a small mostly-Linux fleet), Mid-size SaaS, Enterprise (broad coverage across web, infrastructure and APM with a large fleet) and Regulated Finance. Pick the one closest to the system you are sizing, then adjust.

2. Read the estimate before you send anything

The Stats page shows an estimate of time series and data volume per day for the simulators you have enabled, with a breakdown per simulator. Estate metrics are roughly one series per entity per metric, so fleet size drives cardinality: 20 hosts is a few hundred series, 2,000 hosts is orders of magnitude more. Treat it as a planning number to compare with what your backend actually reports.

3. Ramp up in steps

  1. Run at the default rate for several minutes and record your baseline: ingest rate, CPU and memory of the backend, query latency.
  2. Raise the speed multiplier (0.25× to 10×) — it scales every scenario's send rate without changing batch size or error rate.
  3. Increase fleet sizes (Infrastructure, Containers, Kubernetes) to grow metric cardinality.
  4. Add scenarios, or use Traffic Surge, which multiplies batch volume by ten.
  5. After each step wait a few minutes and compare. The knee in the curve is the finding.

For more than one container's worth of load, start several OTel Studio containers, or use the Job API to run up to 25 independent runs from one place.

4. Test high cardinality deliberately

High cardinality is the usual cause of surprise bills and slow queries. The Cardinality Burst scenario puts a random user ID on every request, which creates a new series or attribute value each time. Run it for a few minutes and watch series counts, memory and query times — and check whether your pipeline has a cardinality limit or drop rule that actually engages.

5. Include the signals you really have

Logs usually outnumber traces, which outnumber metric points. Turn individual signals on and off with the Traces, Logs and Metrics toggles to see which one dominates your cost. Add geo/IP simulation or custom attributes on a scenario to make records wider — wider records cost more to store and index.

6. Compare what was sent with what arrived

Press Reset Stats before a run, and compare the totals afterwards with the backend's own counts. A shortfall points at dropped data: batch or queue limits, rate limits returning HTTP 429, or a collector running out of memory. Check otelcol_exporter_send_failed_* style metrics on your collector as well.

7. Bound the run and clean up

  • Set a time limit (and a webhook) so an unattended test stops by itself.
  • Remember retention: test data stays in your backend. Filter or delete it using synth.generated: true.
  • Do not point load tests at a shared production backend.
What OTel Studio is not. It generates realistic, correlated data and controllable volume; it is not a replacement for load-testing your own applications. Its numbers tell you how a backend copes with this shape of telemetry — a strong guide, not a guarantee of your production profile.

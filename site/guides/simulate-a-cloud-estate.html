Estate

Simulate a Cloud Estate That Lines Up

Hosts, containers, pods and services that share identities — so you can follow an incident from symptom to cause.

Most telemetry generators produce traces and stop there. Real incidents cross layers: a host runs out of memory, a container is OOM-killed, a pod is evicted, and a service that was running on it starts failing. To test dashboards and runbooks that follow that chain, the identities have to line up. OTel Studio's simulators share one pool, so they do.

The chain

Everything starts at Infrastructure, a fleet of 20 to 2,000 hosts with a realistic mix of cloud provider, region and operating system. On top of it:

  • Scenario services are placed on real hosts from the fleet: their resources carry host.name, cloud.provider and cloud.region from a host that exists.
  • Containers are placed on those hosts, and a service that runs in a container carries that container's identity.
  • Kubernetes nodes are placed on hosts, pods on nodes, and services on pods.

The result: take a k8s.pod.name from a trace, find the pod, find its node, and find the host — and the host is the one reporting memory pressure.

Set it up

  1. Open Simulators → Infrastructure, choose a size (Small Team 20, Mid-size 200 or Enterprise 2,000 hosts) and press Start Infrastructure.
  2. Start Containers and Kubernetes from their pages. Both need Infrastructure enabled.
  3. Enable a few scenarios — E-Commerce, SaaS, a Kubernetes control-plane scenario — and press the main Start.
  4. The Dashboard's status strip shows all six simulators and their counts at a glance.

Each simulator starts and stops on its own, with an optional duration, so you can run Kubernetes for ten minutes while Containers runs for five.

What each layer reports

LayerRealistic behaviour
HostsCPU, memory, disk and network metrics, plus swap/paging and iowait that rise with real memory and disk pressure; fleet churn that replaces hosts like auto-scaling.
ContainersA lifecycle of running, restarting, OOM-killed and crashed with Docker's event sequence (including exit code 137); CPU throttling counters; memory as a percentage of the limit.
KubernetesPod phases and failure reasons (OOMKilled, CrashLoopBackOff, ImagePullBackOff, Evicted, Unschedulable); resource requests and limits with the computed QoS class; HPA-style autoscaling; rolling updates; node conditions; control-plane health; an events feed with real reason strings.

Add an incident

Press Inject Incident. OTel Studio picks one host at random, finds the services and pods running on it, and degrades them together for 60 seconds. An [INCIDENT] entry in the activity stream names the host and the affected services. In your backend you should see one host's metrics turn bad while the traces and logs of exactly those services show errors and latency.

Use it to check that your dashboards let an on-call engineer walk from a failing service to the host, that alerts group by the right labels, and that a runbook's first three queries really find the problem.

Things to try

  • Search your backend for a host name from the Infrastructure page and confirm traces, container metrics and pod metrics all reference it.
  • Turn on only Infrastructure: it raises logs and metrics even with no scenario running, which is a cheap way to test host-metric dashboards.
  • Resize the fleet and watch series counts rise — then compare with the Stats estimate.
  • Run the estate for an hour with a time limit and check retention and downsampling behave.

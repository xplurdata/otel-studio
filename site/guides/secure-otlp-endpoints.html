Send OTLP to Secured Backends: Tokens, Headers, TLS and mTLS

Credentials that work the first time — and what each failure actually means.

Real observability backends do not accept anonymous data. They want a token, a tenant, an API key or a client certificate — and getting that wrong produces silence rather than an error you can read. This guide shows how to configure each kind of credential in OTel Studio, and how to tell what a failure means.

Where credentials go

On the Endpoints page, each endpoint has a URL, a protocol, an optional Bearer token and headers section and an optional TLS / mTLS section. Everything is per endpoint, so two backends can each have their own.

Headers

Add any number of headers (up to 20). Names must be valid HTTP header names and values must be a single line. A few headers belong to OTel Studio and cannot be overridden: Content-Type, Content-Length, Content-Encoding, Host and similar. A bad header is refused when you save the endpoint, with a message that names it.

TLS and mutual TLS

  1. For a server certificate signed by a private CA, paste the CA certificate (PEM) so the connection can be verified.
  2. For mutual TLS, add the client certificate and the client private key (both PEM).
  3. The insecure toggle skips certificate verification. Use it only on an isolated test network, never against a production backend.

How secrets are protected

  • Tokens and header values are encrypted at rest with a key derived from JWT_SECRET, which is generated on first start and stored with your data. Keep the /data volume and the secret together — a different secret cannot decrypt old values.
  • After saving, a token is never shown again, and is never returned by the API, the live state stream or a configuration export. Header names stay visible so you can see what is set.
  • Edit an endpoint and leave the token field empty to keep the saved token; use Remove the saved token to clear it. Changes apply to a running simulation straight away, so rotating a token needs no restart.
  • In command-line mode, read the token from an environment variable (OTEL_STUDIO_BEARER_TOKEN, or the variable named by --token-env) — never from a flag, so it does not appear in process lists.

Use the least privilege that works

Create a token that can only ingest: most vendors let you scope keys to write-only. Give test traffic its own tenant, dataset or project so it is easy to find and delete, and rotate the token when the test is over.

Reading the Test result

ResultMeaningTry
AcceptedThe endpoint answered an OTLP request with success.Press Start.
Reachable, but credentials refused (HTTP 401 / 403)You reached the backend and it rejected you.Check the token, the header names and values, the tenant, and whether the key has ingest permission.
Reachable, but not accepted as OTLP (HTTP 404 etc.)Something answered, but not an OTLP receiver at this path.Use the base URL (paths are added for you), the HTTP port (4318) rather than the gRPC port (4317), and check any path prefix such as /otlp or /api/default.
Unreachable (for example ECONNREFUSED)Nothing is listening, or the name does not resolve.Inside a container localhost is the container itself — use a shared Docker network or host.docker.internal.
An easy trap. A gRPC endpoint pointed at an HTTP port, or the reverse, can look connected while no data is stored. If the Test result is fine but your backend is empty, check the protocol matches the port and read OTLP gRPC vs HTTP.

Synthetics

Test Synthetic Monitoring Dashboards and Uptime Alerts

Know it is down before your users do — and prove the alert works.

Synthetic monitoring — scripted checks that call your endpoints from outside on a schedule — is the quickest way to learn that something is down before users tell you. Like any alert, the checks and the rules behind them need testing. This guide covers what a good synthetic check measures, how the data looks in OpenTelemetry form, and how to test your dashboards and alerts using OTel Studio's Synthetics simulator.

What the data looks like

The Collector's httpcheck receiver turns each check into metrics, and OTel Studio's simulator follows the same naming:

MetricMeaning
httpcheck.status1 when the check passed, 0 when it failed; carries http.url, location and http.status_code attributes
httpcheck.response.durationTotal response time in milliseconds
httpcheck.dns.lookup.durationTime spent resolving the host name
httpcheck.tls.handshake.durationTime spent negotiating TLS

Because each check runs from several simulated locations, you also get the one question synthetic monitoring exists to answer: is it down for everyone, or only from one place?

What the simulator checks

  • Checks named after your own URLs (add them under Check Targets), each with an interval, method and expected status code. A check passes when the simulated response matches what that check expects.
  • Assertions beyond the status code: response body content and a maximum response time. Either can fail a check whose status code looks healthy.
  • Retry before failing: a failed attempt is retried (up to twice), as most synthetic tools do, because many failures are transient. The result shows whether it recovered. A small share of check and location pairs fail occasionally, so a realistic amount of noise is always present.
  • Multi-step checks: a login step can extract a token that a later step uses, and a failing step halts the rest of the chain.
  • Locations: choose which simulated regions run each check.
The results are simulated. OTel Studio does not send requests to the URLs you list: it generates the metrics that checks against them would produce, using your names and URLs as labels. That means it is safe to use any name, and it is a data generator for testing dashboards and alerts — not a replacement for a real synthetic monitoring service.

A test plan

  1. Dashboards. Start Synthetics (Simulators → Synthetics) with six checks and several locations. Build panels for pass rate, response time p95 by location, and DNS and TLS time. Check they handle several URLs and locations without clutter.
  2. Uptime alert. Alert when httpcheck.status is 0 for a URL from more than one location for several minutes — single-location blips are usually noise (the simulator produces a few on its own). Force a sustained failure by giving a check a response-time limit that its simulated responses can never meet (for example 10 ms against responses of roughly 50 to 130 ms), confirm the alert fires and notifies, then raise the limit and confirm it resolves.
  3. Latency alert. Alert on httpcheck.response.duration p95 above your threshold. Tighten and relax the check's response-time limit to move the pass rate on demand.
  4. Silence and recovery. Stop the simulator and check your "no data" handling: does a missing check look like a healthy one, or like an outage? Both are common mistakes.

Good practice for real checks

  • Check the user-visible path (login, search, checkout), not only the home page.
  • Run from at least three locations and alert on a quorum.
  • Keep checks fast and idempotent, and mark their traffic with a recognisable user agent so you can exclude it from analytics.
  • Watch certificate expiry separately; it is a calendar problem, not an outage.

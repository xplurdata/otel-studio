OpenTelemetry Data Not Showing Up? A Troubleshooting Checklist

Stop guessing: test one stage at a time, starting with a sender you trust.

"I send OpenTelemetry data and nothing shows up" is the most common OpenTelemetry problem, and it is hard because the pipeline has many stages and most of them fail silently. The way through is to stop guessing and test one stage at a time, starting with a sender you trust. This checklist is ordered from the most to the least common causes.

Step 0: use a known-good sender

If you are not sure whether the fault is in your application or in the pipeline, remove the application from the question. Point OTel Studio at the same endpoint. If its data arrives, your pipeline is fine and the problem is in your instrumentation. If it does not, the problem is downstream of the sender, and everything below applies.

1. Is the endpoint reachable, and is it OTLP?

On the Endpoints page press Test. It reports four different situations:

ResultMeaningNext step
AcceptedThe receiver answered an OTLP requestGo to step 4
Reachable, but credentials refused (HTTP 401/403)The address is right; the token, header or tenant is wrongFix credentials — see Secured Backends
Reachable, but not accepted as OTLP (HTTP 404 etc.)Something is listening, but not an OTLP receiver at this pathStep 2
Unreachable (ECONNREFUSED, timeout)Nothing is listening, a firewall blocks it, or the name does not resolveStep 3

2. Right protocol, right port, right path

  • By convention 4317 is gRPC and 4318 is HTTP. A gRPC exporter pointed at 4318 (or the reverse) can look connected and deliver nothing.
  • For HTTP the paths are /v1/traces, /v1/logs and /v1/metrics. Use the base URL, or a full per-signal URL for that signal only.
  • Some backends put OTLP under a prefix (/otlp, /api/default); include it in the base URL.
  • A proxy in the path may break HTTP/2, which gRPC needs. See gRPC vs HTTP.

3. Networking, especially in containers

  • Inside a container, localhost is the container. Use the target's container name on a shared Docker network, or host.docker.internal for the host.
  • In Kubernetes use the service DNS name and check NetworkPolicies and the namespace.
  • Confirm the Collector's receiver is bound to 0.0.0.0, not localhost, if traffic comes from another container or host.

4. Is the Collector dropping it?

If the receiver accepted the data, look inside the Collector:

  1. Add a debug exporter with verbosity: detailed to the pipeline. If records print here but not in the backend, the problem is after this point.
  2. Check every pipeline. A signal needs a pipeline of its own; metrics sent to a Collector that only has a traces pipeline are accepted and discarded.
  3. Check processors that filter, sample or limit. A filter rule, a tail_sampling policy or a memory_limiter can drop data without errors in the sender. See Test Tail Sampling.
  4. Read the Collector's own metrics and logs for refused or dropped counts and exporter send failures.

5. Is the backend rejecting or hiding it?

  • Authentication, tenant and project headers; ingest quotas and rate limits (HTTP 429).
  • Time range: data with timestamps outside the window you are viewing, or a host clock that is wrong.
  • Delta versus cumulative metrics: some backends accept only one.
  • Attribute or series limits that silently drop new data. See High Cardinality.
  • Filtered views: if you are looking at production views, synthetic data marked synth.generated may be excluded.

6. Only now suspect the application

If a known-good sender works end to end but your application does not, check: the SDK is configured with the endpoint and protocol you think; the exporter is not blocked by an environment variable overriding it; spans are ended (unended spans are never exported); the process flushes on exit (short-lived jobs often exit before the batch is sent); sampling is not set to zero; and the service name is what you are searching for.

The principle. Change one thing, observe, and move one stage along. A sender you trust turns "the pipeline is broken somewhere" into "it works up to here" — which is most of the way to the fix.

Real User Monitoring With OpenTelemetry: Web Vitals and Trace Correlation

What users really experience — and how to build the dashboards before they arrive.

Real user monitoring (RUM) measures what visitors actually experience in their browsers: how fast pages become usable, whether clicks work, which errors they hit. Pairing it with backend traces answers the hardest question — was the slow page caused by the browser or the server? This guide explains the signals and how to build and test RUM dashboards without waiting for real traffic.

The signals that matter

SignalWhat it tells youRule of thumb (good)
LCP — Largest Contentful PaintHow quickly the main content appears2.5 seconds or less
INP — Interaction to Next PaintHow responsive the page is to input200 ms or less
CLS — Cumulative Layout ShiftHow much the page jumps around while loading0.1 or less
TTFB — Time to First ByteServer and network time before anything arrivesCompare against your own baseline
FCP — First Contentful PaintWhen anything first rendersCompare against your own baseline
Frustration signalsRage clicks (many rapid clicks) and dead clicks (clicks that do nothing)Rising counts mean broken UI
JavaScript errorsExceptions with a stack, file and line, grouped by fingerprintGroup by fingerprint, not by message

LCP, INP and CLS are the Core Web Vitals; judge them at the 75th percentile of page loads, not the average.

Connecting the browser to the backend

A browser SDK can send the W3C traceparent header with its requests, so the server joins the browser's trace. Then a slow page load shows the whole story in one trace: the browser's page load span, the API call it made, and every service behind it. OTel Studio's RUM simulator reproduces this: for a window after a session starts, a share of Web App scenario traces (E-Commerce, SaaS, Media Streaming, Banking, Social Network) use the session's page-load span as their root, so they genuinely share a trace ID. You choose the correlation rate.

Try it with synthetic sessions

  1. Start RUM (Simulators → RUM). Set the application name to match your real service name, so data groups sensibly. Choose how many sessions can be active at once and how often a new one starts.
  2. Start a Web App scenario beside it, with a correlation rate above zero.
  3. Build panels: p75 of each vital by page, sessions by browser and device, error counts by fingerprint, and a funnel from the named milestones such as "Checkout Complete" and "Signup Complete".
  4. Open a correlated trace and confirm the browser span is the root, with the backend services below it.

Sessions carry browser, operating system, viewport and connection-type attributes, so you can test breakdowns by device class too.

Alerts worth testing

  • p75 LCP over 2.5 seconds for a key page for ten minutes.
  • A new error fingerprint appearing, or a known one affecting more sessions than usual.
  • A sudden drop in a conversion milestone while traffic is steady.
  • Rage-click rate above its baseline on checkout pages.

Two modes

The default simulator generates session data directly, which is fast and needs no browser. If you want a real browser to visit your own instrumented site and produce genuine data, use the -browser image; see Real-browser RUM in the documentation.

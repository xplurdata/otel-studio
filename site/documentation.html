OTel Studio

Generate realistic OpenTelemetry data for any observability stack

OTel Studio is a Docker-deployable telemetry data generator that produces correlated traces, logs and metrics using realistic service topologies. Point it at any OTel-compatible backend and get production-like data flowing in 60 seconds.

Overview

OTel Studio is the data source you do not have yet. It produces realistic OpenTelemetry traces, logs and metrics — as if from a real estate of services, hosts, containers, clusters, browsers and AI workloads — and sends them over OTLP to your collector or backend. Nothing in your own applications changes. Use it to prove a pipeline works, to build and test dashboards and alerts, to size and load-test a backend, or to demo a stack with traffic that looks real.

Key terms: a scenario is an application topology (for example E-Commerce) that produces traces, logs and metrics; a simulator is one of the six estate generators; an endpoint is a destination for the data; a run is a period during which data is sent. Everything OTel Studio sends carries synth.generated: true, so your backend can filter it out of production views.

Quick Start

bash 
docker run -d --name otel-studio -p 3002:3002 \
  -e OTEL_ENDPOINT="http://your-collector:4317" \
  -e OTEL_PROTOCOL="grpc" \
  ghcr.io/xplurdata/otel-studio:latest

Open http://localhost:3002 and log in as admin. ADMIN_PASS is optional — if you don't set it, a random password is generated on first boot and printed once in the container logs (docker logs otel-studio). Set ADMIN_PASS explicitly if you want to choose your own instead.

You can also start the container without OTEL_ENDPOINT: OTel Studio has no built-in destination, so nothing is sent until you add your OTLP backend or collector on the Endpoints page (the Dashboard reminds you, and Start asks for an endpoint first).

Architecture

OTel Studio
→
OTLP gRPC / HTTP
→
OTel Collector
→
Your Backend

Traces, logs and metrics are sent via standard OTLP protocol — works with any OTel-compatible backend

OTel Studio uses the official OpenTelemetry JS SDK. Each scenario creates a BasicTracerProvider per service name, with one BatchSpanProcessor per active endpoint. Logs use LoggerProvider with one BatchLogRecordProcessor per active endpoint. Metrics use a shared MeterProvider with one PeriodicExportingMetricReader per active endpoint — this is what makes multi-endpoint fanout work for all three signal types, not just traces.

All three signals are correlated — logs emitted during a trace span inherit the span's trace ID and span ID via OpenTelemetry context propagation. This means you can search for a trace ID in your backend and see the matching logs and metrics.

Docker Configuration

bash 
docker run -d --name otel-studio -p 3002:3002 \
  -e OTEL_ENDPOINT="http://otelcol:4317" \
  -e OTEL_PROTOCOL="grpc" \
  -e SERVICE_NAME="otel-studio" \
  -e ENVIRONMENT="production" \
  -e ADMIN_PASS="secure-password" \
  -e MODE_REAL="true" \
  -e MODE_SIM="true" \
  --group-add "$(stat -c %g /var/run/docker.sock)" \
  -v /var/log:/var/log:ro \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v otel-data:/data \
  --memory=256m \
  ghcr.io/xplurdata/otel-studio:latest
JWT_SECRET is optional — if omitted, OTel Studio generates a random one on first boot and persists it in the mounted /data volume, so it stays stable across restarts without needing to be set manually. Pass -e JWT_SECRET="..." explicitly only if you're running multiple replicas that need to share one signing secret.
Runs as a non-root user. The container runs as the unprivileged user node (uid 1000), and /data is the only place it writes. A named volume works as is; a bind mount must be writable by uid 1000 (chown 1000:1000). For Real System Data, the Docker socket needs the --group-add line shown above, and the log files you mount must be readable by uid 1000 — if they are not, run with --user root instead. In the image the process is started by tini, so docker stop flushes pending telemetry and exits within a second or two.

Deployment Recipes

Docker Compose

bash 
services:
  otelcol:
    image: otel/opentelemetry-collector-contrib:latest
    volumes: ["./otelcol.yaml:/etc/otelcol-contrib/config.yaml:ro"]
  otel-studio:
    image: ghcr.io/xplurdata/otel-studio:latest
    ports: ["3002:3002"]
    environment:
      ADMIN_PASS: ${ADMIN_PASS:?set ADMIN_PASS}
      OTEL_ENDPOINT: http://otelcol:4317
      OTEL_PROTOCOL: grpc
    volumes: ["studio-data:/data"]
    depends_on: [otelcol]
    restart: unless-stopped
volumes:
  studio-data: {}

Both services share the Compose network, so otelcol resolves by name.

Run one replica: the live state is held in the process. Create the otel-studio secret and the otel-studio-data claim first.

Behind a reverse proxy (TLS)

OTel Studio serves plain HTTP; terminate TLS in front of it and set TRUST_PROXY=1. The live activity stream (/events) is a long-lived connection, so turn proxy buffering off for it:

bash 
server {
  listen 443 ssl;
  server_name studio.example.com;
  # ssl_certificate ... ;

  location / {
    proxy_pass http://127.0.0.1:3002;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
  }
  location /events {
    proxy_pass http://127.0.0.1:3002;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_read_timeout 1h;
  }
}

Use Cases

Check a collector pipeline end to end

  1. Add your collector's OTLP URL on the Endpoints page and press Test — it tells you whether the address is reachable, whether the credentials are accepted and whether it speaks OTLP.
  2. Pick a scenario, press Start, and let it run for a few minutes.
  3. Compare the totals on the Stats page (after the last Reset Stats) with what the collector and your backend received. A gap means data was dropped or refused on the way.

Test an alert rule or an SLO

  1. Run a scenario at a steady rate with a low error percentage, and confirm your alert is quiet.
  2. Press Inject Anomaly: for 30 seconds traffic is multiplied by ten and 80% of requests fail. Check the alert fires, notifies and resolves.
  3. For a host-level story, enable Infrastructure and press Inject Incident: one host degrades and the services running on it show matching errors and latency.

Load-test a backend and estimate cost

  1. Choose the Enterprise template on the Scenarios page and enable the simulators you care about.
  2. Read the estimated time series and data volume per day on the Stats page before you start.
  3. Raise the speed multiplier (up to 10×) or enable the Cardinality Burst scenario, set a time limit, and watch your backend's ingestion and query behaviour.

Compare two backends with identical data

  1. Add both as endpoints, each with its own token, headers and TLS settings.
  2. Activate both. Every signal is sent to each active endpoint, so the two receive the same traffic at the same time.

Run a check in CI

bash 
docker run --rm -e OTEL_STUDIO_BEARER_TOKEN="$TOKEN" \
  -v $PWD/demo.yaml:/app/demo.yaml:ro ghcr.io/xplurdata/otel-studio:latest \
  node dist/headless.js --config demo.yaml --duration 60s \
  --endpoint https://collector.example.com:4318

The exit code is 0 only when the run finished and everything was flushed, so it works as a pipeline step. To start many runs from another tool, use the Job API.

Demo or train on a stack

  1. Pick a Quick Start Template (for example Mid-size SaaS) for a ready scenario and fleet profile.
  2. Turn on Sequential mode to rotate through scenarios automatically, and set a time limit (with an optional webhook) so an unattended demo stops on its own.

Signal Types & Ratios

Per the OpenTelemetry specification, the three signal types have different volume characteristics:

SignalVolumeHow OTel Studio generates it
LogsHighestOne log record per service visited in each trace chain. A 5-service chain produces 5 logs per trace.
TracesMiddleOne trace chain per batch item, containing 10-15 spans with parent-child relationships.
MetricsLowestAggregated per export cycle (10s interval). Each cycle exports one data point per unique instrument, regardless of request volume.

Each of Traces, Logs, and Metrics can be toggled independently in the top control bar — turning a signal off stops it from being generated across every active scenario at once.

Advanced Scenario Controls

Every scenario card has an Advanced Settings panel with telemetrygen-style controls for testing specific pipeline behaviors:

Geo / IP Simulation

Tags the root span and logs of each generated request with a client.address and GeoIP-resolvable attributes (geo.country.iso_code, geo.city.name, geo.location.lat/lon, cloud.region), so requests appear to originate from realistic global locations. Two modes, set globally on the Endpoints page:

ModeBehavior
RealisticReal regional cloud IP ranges — resolves to an actual city/country in your backend's GeoIP lookup
Safe / TEST-NETRFC 5737 non-routable ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) — guaranteed to never collide with real infrastructure, at the cost of not resolving to a real location

Synthetic PII

Tags the root span and logs with a synthetic user.id, user.name, and user.email, generated from a fixed name pool and RFC 2606-reserved domains (example.com/.org/.net) — never real people's data. Every synthetic record is marked with pii.synthetic: true so a downstream redaction/DLP pipeline being tested can positively identify it. Recommended for scenarios like Banking, Social Network, and E-Commerce where testing PII handling is relevant.

Custom Attributes

Arbitrary key=value pairs, comma-separated, added to the root span and logs of every request in that scenario — useful for tagging generated data with a team name, region, or any attribute your dashboards filter on.

Span Duration Override

Set a min/max range in milliseconds to override the scenario's natural randomized timing. Leave blank to use built-in realistic chain timing.

Status Code Weights

code:weight pairs, comma-separated (e.g. 200:90,404:5,500:5) — controls the distribution of HTTP status codes on generated spans. When set, this overrides the scenario's plain error-rate slider.

Anomaly Injection

Click ⚡ Inject Anomaly to trigger a burst across all active scenarios. For 30 seconds (or until you click Stop Anomaly):

Traffic10× normal batch count
Error rateForced to 80% regardless of slider
Latency30% of spans get 2-8 second duration spikes

Anomaly state is tracked server-side and stays in sync with the main Start/Stop control — stopping the simulation (manually or via quota expiry) also clears an in-progress anomaly, and the button/timer reflect this on any connected browser tab, not just the one that triggered it.

Sequential Mode

Enable Sequential Mode in the Scenarios panel to run one scenario at a time, rotating through all enabled scenarios on a configurable timer (default 30 seconds each). Useful for sequential load testing — each scenario runs in isolation before rotating to the next.

Inject Incident

Click 🔥 Inject Incident to degrade one host for 60 seconds. OTel Studio picks a host at random from the simulated Infrastructure fleet and finds the services and pods running on it, so the incident is one coherent story rather than unrelated random changes: the host's CPU, memory and disk metrics turn bad, and the services placed on it show matching errors and latency in their traces and logs. An entry marked [INCIDENT] names the host and the affected services in the Activity Stream. Click Stop Incident to end it early.

Inject Incident needs Infrastructure Simulation to be enabled, because there is no host fleet to target otherwise.

Time Limit / Quota

Set a time limit (1m / 5m / 10m / 30m / 1h / no limit) before clicking Start. The top bar shows a live countdown; when it reaches zero, sending stops automatically across all signals — including metrics, which export on their own periodic schedule independent of the trace/log generation loop.

Infrastructure

Generates a fixed pool of simulated hosts with realistic cloud provider, region, and OS distributions. This isn't cosmetic — it's the identity source every other simulator correlates to. When enabled, every scenario's service gets assigned a real host from this same pool via host.name, cloud.provider, and cloud.region resource attributes. Each host also independently emits its own CPU/memory/disk/network metrics and OS-level logs, raising LOGS and METRICS in the top bar even with no scenario running.

Quick Start presets (Small Team / Mid-size Company / Enterprise) set a realistic host count and OS mix in one click. Advanced Settings expose cloud placement (provider/region selection), exact CPU/memory tier allocation per OS, fleet churn (periodic host replacement simulating real auto-scaling), and a configurable host-role pool — leave any of these empty to use sensible built-in defaults.

Beyond CPU/memory/disk/network, each host also reports swap/paging utilization (system.paging.utilization) and CPU iowait, both genuinely correlated to that host's actual memory and disk pressure rather than independent random values — a host under real memory pressure shows real swap activity, not a coincidentally-elevated number.

Containers

Generates a container fleet, each container correlated to a real host from the Infrastructure fleet — not a separate, disconnected identity. Requires Infrastructure also enabled. Compose Service grouping lets you filter the container table by service and see a live per-service count breakdown, matching a real docker-compose.yml's "services:" section. The image pool (which container images appear) is fully configurable in Advanced Settings, falling back to a built-in default library (nginx, postgres, redis, etc.) when left empty.

Each container has a real lifecycle: normal running, restarting, OOM-killed, or crashed, with a matching event timeline (create → start → oom → die with the real exitCode=137 OOMKilled signature, etc.) grounded in Docker's own documented event vocabulary. A small realistic minority of containers also show genuine CPU throttling (container.cpu.throttling_data.throttled_periods/throttled_time — real Docker Stats receiver metrics), and memory is tracked as percent-of-limit, not just raw usage — the signal that actually predicts an OOM kill.

Kubernetes

The deepest correlation chain in the app: Pod → Node → real Infrastructure Host. Every pod is placed on a real node, and every node is placed on a real Infrastructure host — verified directly against generated data, not assumed. Requires Infrastructure also enabled.

Pod phases (Running/Pending/Succeeded/Failed) and failure reasons (OOMKilled, CrashLoopBackOff, ImagePullBackOff, Evicted, Unschedulable) match the real Kubernetes API vocabulary exactly — not invented values. The Events feed (both a cluster-wide view and per-pod in the drill-down modal) uses real event reason strings and message formats sourced directly from the Kubernetes source code (pkg/kubelet/events/event.go), so a pod's event timeline genuinely tells a coherent story: Scheduled → Pulling → Pulled → Created → Started for a healthy pod, or that same sequence ending in a Warning: Killing event for one that got OOMKilled.

Every pod also carries real resource requests/limits and a genuine QoS class (Guaranteed, Burstable, BestEffort) computed by the actual Kubernetes algorithm — Guaranteed pods have requests exactly equal to limits, Burstable have limits set higher, BestEffort have neither. Deployments support real HPA-formula autoscaling (desiredReplicas = ceil(current × currentCPU/targetCPU), including the real ±10% tolerance band) and rolling-deployment simulation with genuine availableReplicas dips during rollout. Each cluster also reports control-plane health — API server and etcd latency/error-rate, since an overloaded API server is a real, commonly-unmonitored failure mode that can block scaling or deployments entirely.

Synthetics

Simulates HTTP checks named after your own URLs, run from multiple simulated locations and independent of any scenario — modeled on the OTel Collector's http_check receiver, using the same httpcheck.* metric names. The results are generated: OTel Studio does not send requests to the URLs you list, it produces the telemetry such checks would produce, using your names and URLs as labels. Each check has a configurable interval, HTTP method, and expected status code — the pass/fail result is a genuine comparison against what that specific check expects, not a fixed random rate. SSL certificate expiry is computed per check and surfaced directly on the main table (not buried in a drill-down), color-coded when expiry is under 30 days.

Beyond status codes, checks can assert on response body content (matching real synthetic-monitoring tools that verify payloads, not just status) and a maximum response-time threshold — either can independently fail a check even when the status code itself looks healthy. Multi-Step Checks chain requests together with the same variable-extraction/reuse pattern real tools like Datadog use (e.g. a login step's token feeding into a later authenticated request), and a failing step genuinely halts the rest of the chain rather than continuing regardless. Failed checks also get retried (matching the real retry-before-alert pattern most synthetic monitoring tools use, since many failures are transient blips, not genuine outages) — the drill-down shows whether a result recovered after a retry or genuinely failed.

Add your own check targets in "Check Targets" — once you add at least one, your custom targets fully replace the built-in defaults.

RUM (Real User Monitoring)

Periodically starts simulated browser sessions (one page-load span carrying Core Web Vitals — LCP, INP, CLS, TTFB, FCP — plus browser/OS/viewport/connection-type attributes), with configurable concurrency so multiple sessions can genuinely be active at once, matching real traffic with many simultaneous users. For a window afterward, a subset of Web App group scenario traces (ecommerce, saas, media, banking, social) get linked to a randomly-chosen active session as their root parent via real OpenTelemetry context propagation — the resulting trace genuinely shares the same trace ID from the simulated page load through the backend service chain, not just a similar timestamp.

Sessions also generate rage/dead-click frustration signals, and JS errors are recorded with a real stack trace, source file/line, and a fingerprint hash so recurring errors group together with an affected-session count — matching how real error-tracking tools deduplicate rather than showing every occurrence as an unrelated line. Named business milestones ("Checkout Complete", "Signup Complete", etc.) are tracked per page with a genuine, probabilistic completion rate, surfacing real conversion-funnel-style data rather than every session completing every milestone.

Application Name sets the service.name resource attribute on every session span — set this to match your real app's name so the simulated RUM data groups correctly alongside anything else your backend already receives. Browser Pool and Device Types (Advanced) let you restrict sessions to specific browsers or device categories, useful for testing how a dashboard looks under mobile-only or Safari-only traffic.

Real-browser RUM (browser image)

Besides the simulated RUM sessions above, OTel Studio can drive a real headless Chromium against a website of yours that already has a RUM or OpenTelemetry browser SDK installed, so the browser itself produces the real session data (page loads, clicks, JavaScript errors) from different countries. This needs the -browser image; the default image has no browser and refuses to start it with a clear message. It is configured through the API, not the UI.

bash 
docker run -d --name otel-studio -p 3002:3002 \
  -e RUM_TARGET_URL="https://your-site.example" \
  -v $(pwd)/rum-paths.json:/config/rum-paths.json:ro \
  ghcr.io/xplurdata/otel-studio:latest-browser

rum-paths.json lists the pages to visit, relative to RUM_TARGET_URL: {"paths": ["/", "/pricing", "/checkout"]}. With a session cookie from POST /api/login, turn it on:

bash 
curl -b cookies.txt -X POST http://localhost:3002/api/control -H "Content-Type: application/json" \
  -d '{"rumBrowser": {"enabled": true, "pathsFile": "/config/rum-paths.json", "visitsPerTick": 3, "intervalSec": 45}}'
curl -b cookies.txt -X POST http://localhost:3002/api/control/pillar -H "Content-Type: application/json" \

AI Observability

Simulates LLM API calls across 8 models spanning 5 major providers — OpenAI, Anthropic, Google, DeepSeek, and xAI, deliberately balanced rather than weighted toward any single provider. Each call emits the real, spec-confirmed OTel GenAI metrics (gen_ai.client.token.usage, gen_ai.client.operation.duration, gen_ai.server.time_to_first_token, gen_ai.server.time_per_output_token), plus cost computed from real, current per-model pricing.

Quality/safety scoring (groundedness, relevance, PII/prompt-injection detection) and RAG/agent-specific metrics (context relevancy, tool-selection accuracy) are deliberately emitted under a custom llm.* namespace rather than gen_ai.*, since these genuinely aren't part of the official OTel GenAI semantic conventions — confirmed directly against the spec, which "has no concept of faithfulness or groundedness scoring." Four independent failure-injection toggles are available: cost spike (runaway generation), latency spike, elevated error rate, and quality degradation (elevated hallucination/low-groundedness rate) — matching the real, most-cited production pain points for LLM applications.

Per-Simulator Start/Stop

Each of the six simulators (Infrastructure, Containers, Kubernetes, Synthetics, RUM, AI Observability) has its own independent Start/Stop control with an optional duration, separate from the global Start/Stop in the top bar. A simulator is actively generating data if either the global run is active or that simulator's own independent run is active — clicking a simulator's own Start both enables it and starts it together in one action; Stop only pauses generation, leaving the configuration saved for next time.

This means you can run, for example, Kubernetes for 10 minutes and Containers for 5, completely independently, without the global Start/Stop affecting either — set each simulator's own Duration field and click its own Start button.

Cross-Simulator Identity

Every identity in this app resolves to the same underlying pool, not separate stub generators per simulator. A Scenario's service gets assigned a real host from the Infrastructure fleet; when Containers is enabled, that same service also correlates to a real entry in the Container fleet; when Kubernetes is enabled, it correlates to a real pod on a real node. Search for a host.name, container.id, or k8s.pod.name from a Scenario trace in your backend, and you'll find the exact same identity listed on that simulator's own page — not a coincidentally-similar one.

Synthetic Marking

Every signal this app generates — every trace, log, and metric, including RUM sessions — carries synth.generated: true and synth.generator: "otel-studio" as resource attributes, set once at the SDK's resource construction rather than added per-signal. Use this to filter synthetic test traffic out of production views in your backend, or to confirm a given signal genuinely came from this tool.

Multi-Endpoint Fanout

OTel Studio can send telemetry to multiple collectors simultaneously. On the Endpoints page, each endpoint has its own toggle — check any combination to activate them together; at least one must stay active. The SDK creates one BatchSpanProcessor, one BatchLogRecordProcessor, and one metric reader per active endpoint, so traces, logs, and metrics all fan out identically. Use this to compare two o11y backends side-by-side or to send to both production and staging collectors at once.

TLS / mTLS

Each endpoint supports an optional TLS/mTLS configuration, expandable in the Add/Edit Endpoint form: a CA certificate, a client certificate, a client private key (all PEM format), and an "insecure" toggle to skip certificate verification for testing against self-signed backends.

Endpoint URL, Bearer Token & Headers

Every endpoint takes a URL, a protocol and, optionally, a bearer token and extra request headers. Authentication is optional: a collector on a private network needs none.

SettingHow it works
URLGive the base URL, for example https://collector.example.com:4318. For HTTP, OTel Studio adds /v1/traces, /v1/logs and /v1/metrics. A URL that already ends in one of those paths is used as given for that signal; the other signals use the same host and base path. For gRPC give host:port or a full URL.
Protocolhttp (OTLP over HTTP, protobuf — the default and accepted by every OTLP receiver), http/json (OTLP over HTTP, JSON) or grpc.
Bearer tokenSent as Authorization: Bearer <token> on every request. It is stored encrypted, never shown again after saving and never returned by the API, the live state stream or exports. Leaving the field empty when editing keeps the saved token; "Remove the saved token" clears it.
Extra headersAny number of name/value pairs, up to 20 — for example X-Scope-OrgID for a multi-tenant backend or api-key. Values are stored encrypted like the token and only the names are shown after saving.

Header names must be valid HTTP header names and values must be a single line. Content-Type, Content-Length, Content-Encoding, Host and similar headers are set by OTel Studio and cannot be overridden. An invalid header is refused when you save the endpoint.

The Test button sends an empty OTLP request in the endpoint's own encoding and tells the cases apart: accepted, reachable but credentials refused (HTTP 401/403), reachable but not accepted as OTLP (for example HTTP 404), or unreachable. Changes to a token or header apply to a running simulation straight away.

Security

AreaWhat OTel Studio does
Sign-inPasswords are stored as bcrypt hashes. The session is a signed token in an HttpOnly, SameSite=Lax cookie that is also Secure over HTTPS. After 10 failed attempts for the same user name from the same address within 15 minutes, further attempts are refused with HTTP 429 until the window ends (LOGIN_MAX_FAILURES, LOGIN_WINDOW_MIN).
Initial adminSet ADMIN_PASS, or a random password is generated on first start and printed once in the container log. There is no built-in default password.
Stored secretsBearer tokens and header values of endpoints are encrypted at rest with a key derived from JWT_SECRET, and are never returned by the API, the live stream or exports. Keep the /data volume and JWT_SECRET together: a different secret cannot decrypt old values.
Browser protectionsResponses carry X-Content-Type-Options, X-Frame-Options: DENY, a frame-ancestors 'none' policy, Referrer-Policy and Permissions-Policy; Strict-Transport-Security is added over HTTPS.
Job APINeeds API_TOKEN (at least 16 characters), compared in constant time. Endpoint tokens in a request are passed to the run through its environment and never written to disk.
PrivacyThe server contacts only the endpoints you add (and the URLs of synthetic checks you define). The web interface loads its fonts and icons from the image itself, so the browser makes no request to any third-party host and the UI works on an isolated network.
ImageNon-root user, build output only (no source files), pinned dependency versions from a lockfile, scanned for HIGH and CRITICAL vulnerabilities, and published with a software bill of materials (CycloneDX).

Deployment advice. OTel Studio serves plain HTTP. For anything beyond a trusted network, put it behind a reverse proxy that terminates TLS, and set TRUST_PROXY=1 so client addresses and HTTPS are read from X-Forwarded-* headers (or COOKIE_SECURE=true to always mark the cookie Secure). Do not expose port 3100 (Job API) publicly. Report vulnerabilities privately as described in SECURITY.md.

FAQ

Does OTel Studio send data anywhere except my endpoints?

No. The server contacts only the endpoints you add, plus the URLs of any synthetic checks you define. The web interface loads its fonts and icons from the image, so it makes no third-party requests and works on an isolated network.

Is the data real?

No — it is synthetic but realistic, and every signal is marked synth.generated: true. The optional Real System Data mode, if you enable it, reads the host's actual log files and Docker metrics.

How do I remove test data from my backend afterwards?

Filter or delete on synth.generated, or on a run-wide attribute you set (--attr test.run=... in command-line mode and the Job API). Sending test traffic to its own tenant, dataset or project makes clean-up trivial.

Can I run several instances?

Yes, with separate /data volumes. For many concurrent runs from one place use the Job API (up to 25 at once).

Does it run on Windows and macOS?

Anywhere Docker runs, including Docker Desktop and Apple Silicon (the image is built for linux/amd64 and linux/arm64).

Why do I see more logs than traces?

By design: one log record is written for every service a request visits, so a five-service chain produces five logs per trace. This matches how real systems behave.

What is the licence?

MIT. There is no account, licence check or usage reporting.

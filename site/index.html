Quick Start

bash 
docker run -d --name otel-studio -p 3002:3002 \
  -e ADMIN_PASS="your-password" \
  -v otel-data:/data \
  ghcr.io/xplurdata/otel-studio:latest

If your collector runs in Docker too, add --network <your-network> so the hostname in OTEL_ENDPOINT resolves — see Docker Configuration for details.

Open http://localhost:3002, add your OTLP backend on the Endpoints page (or pass -e OTEL_ENDPOINT=...), and press Start. The image runs on linux/amd64 and linux/arm64. Need real-browser RUM? Use the latest-browser tag, which also includes Chromium. See Image Variants.

A whole estate, not just traces

Six simulators run alongside the application scenarios and share one pool of hosts, services and identities — so a host, its containers, its pods and the traces running on it all line up in your backend.

Live control room

Counters, sparklines, a simulator status strip and a live activity stream with copyable trace IDs. Start, stop, speed up, inject anomalies.

Infrastructure

Host fleets from 20 to 2,000 with a realistic cloud, region and OS mix, fleet churn, and CPU, memory, swap and iowait metrics that move together.

Kubernetes

Clusters, nodes with health conditions, pods with requests and limits, autoscaling deployments, and an events feed that uses real reason strings.

AI Observability

LLM calls across eight models with the OpenTelemetry GenAI metrics, cost, latency, quality and safety scores, and switchable failures such as cost spikes and hallucination.

Real User Monitoring

Concurrent browser sessions with Core Web Vitals, rage and dead clicks, JavaScript errors and funnels, correlated to backend traces by trace ID.

Synthetics & Containers

Single and multi-step HTTP checks with assertions, retries and SSL-expiry warnings, plus container fleets with OOM kills, crashes and CPU throttling.

Frequently asked questions

Does it send any data to XplurData?

No. OTel Studio only sends telemetry to the endpoints you add, and has no account, licence check or usage reporting.

Can I run it in CI or from my own tools?

Yes. Command-line mode runs for a fixed time and exits with a status code, and the Job API starts, lists and stops runs over HTTP. See the documentation.

Why are there two image tags?

The default image (latest, about 290 MB) contains OTel Studio only and covers everything except one feature. latest-browser (about 1.1 GB) adds Chromium for real-browser RUM, where a headless browser visits your own instrumented website. Most people never need it, so it is kept out of the default image. Both support linux/amd64 and linux/arm64.

Does OTel Studio require any changes to my application code?

No. OTel Studio generates telemetry independently — it doesn't instrument or touch your actual application at all. It sends realistic OTLP traces, logs, and metrics directly to your collector or backend, so you can validate dashboards, alerts, and pipeline configuration without deploying anything to your real services.

Can this replace testing with real production traffic?

No, and it isn't meant to. Real traffic will always surface things synthetic data can't. What OTel Studio is for is everything before that — validating that your collector config, dashboards, and alert rules actually work at all, before you have real traffic to test against, or when you need controllable, repeatable error/latency conditions that real traffic won't reliably give you on demand.

Does it work with self-hosted and on-premise observability stacks?

Yes — OTel Studio speaks standard OTLP (gRPC, or HTTP as protobuf or JSON) to any compatible endpoint, self-hosted or cloud. The one-click stack presets cover 13 popular backends, but any OTLP receiver works, including a self-hosted OpenTelemetry Collector, Grafana stack, Jaeger, or your own custom pipeline.

How is this different from telemetrygen or hand-written test scripts?

Those tools are great for sending a single, precise OTLP payload to test one specific rule. OTel Studio is built for the opposite case — realistic, correlated traffic across many simulated services at once, with logs that share trace IDs with the spans that produced them, controllable error rates and latency spikes, and a UI so you can adjust scenarios live instead of editing a script and re-running it.

Is the generated data actually realistic, or just random noise?

Each of the 30 scenarios models a genuine service topology — real parent-child span chains, realistic log messages per service (JVM GC pauses, Kubernetes OOMKills, gRPC deadline errors, and similar), and natural signal ratios where logs outnumber traces the way they do in real systems. It's synthetic, but built to resemble what an actual distributed system produces, not randomized filler.

Can I send data to more than one backend at the same time?

Yes — multi-endpoint fanout is built in, with independent TLS/mTLS configuration per endpoint. Useful for comparing two backends side by side, or validating a migration before cutting traffic over entirely.

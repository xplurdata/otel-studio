Telemetry reference

The attributes and metrics OTel Studio produces, for building dashboards, alerts and pipeline filters.

This page lists what OTel Studio puts on the wire, so you can build dashboards, alert rules and pipeline filters against it. Names follow the OpenTelemetry semantic conventions wherever a convention exists; anything that is not part of a convention uses a clearly separate prefix (llm.*, synth.*). Backends may rewrite metric names (for example adding _total or unit suffixes in Prometheus), so check how yours maps them.

Signal shape

SignalWhat you get
TracesOne trace per request, with 10–15 spans and correct parent-child links across the services of a scenario. Each service is its own service.name. Failed requests are marked with an error status.
LogsOne log record for every service a request visits, with severity, a realistic message, and the trace_id and span_id of the span active when it was written — so searching a trace ID in your log backend finds the matching records.
MetricsRecorded on a 10-second export cycle with delta temporality. Application metrics are shared across scenarios; estate simulators add their own per-entity series.

RUM and synthetics

  • RUM sessions emit a page-load span carrying Core Web Vitals (LCP, INP, CLS, TTFB, FCP) and browser, operating system, viewport and connection attributes (for example browser.name), frustration signals (rage and dead clicks), JavaScript errors with stack trace, file, line and a fingerprint, and conversion milestones. A share of Web App scenario traces share a session's trace ID.
  • Synthetics follow the Collector's httpcheck receiver: httpcheck.status, httpcheck.response.duration, httpcheck.dns.lookup.duration and httpcheck.tls.handshake.duration, plus an SSL certificate-expiry value per check.

Filtering synthetic data

Everything OTel Studio sends carries synth.generated: true as a resource attribute. To keep it out of production views, add a filter on that attribute in your backend, or drop it in your Collector:

processors:
  filter/synthetic:
    error_mode: ignore
    traces:
      span:
        - 'resource.attributes["synth.generated"] == true'
    logs:
      log_record:
        - 'resource.attributes["synth.generated"] == true'
    metrics:
      metric:
        - 'resource.attributes["synth.generated"] == true'

To keep only synthetic data in a test environment, invert the condition.
